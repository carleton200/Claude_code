# The Tin Heart Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build "The Tin Heart", a single-file browser crafting game in which you combine alchemical ingredients into 5 heart parts and install them in a clockwork companion. Back it with a committed Playwright test suite.

**Architecture:** The whole game lives in `index.html` (inline CSS and JS, no libraries). The JS has two parts. A pure logic core holds data, state transitions and persistence, and is exposed as `window.TinHeart` so tests can call it through `page.evaluate`. A DOM layer renders state and handles clicks and drags. Tests run with `@playwright/test` against a zero-dependency Node static server.

**Tech Stack:** HTML5, CSS, vanilla ES2020 JavaScript, inline SVG, Web Audio (optional), Node 26, `@playwright/test` (Chromium only).

**Spec:** `docs/superpowers/specs/2026-11-16-tin-heart-design.md`

## Global Constraints

- The game is one file, `index.html`, at the repo root. All CSS and JS are inline. Only relative paths. No build step. No external libraries, fonts or network requests.
- It must work from GitHub Pages and when opened from disk (`file://`).
- Starting items: Brass, Ember, Quicksilver, Moth Wing. There are exactly 20 recipes, and the 20 results are all distinct.
- Heart slots: Left Chamber, Right Chamber, Flutter Valve, Spark Core, Rhythm Spring. Each slot accepts only its matching part.
- Items are never consumed. Recipes are order-independent. Self-combine is allowed.
- A hint appears after 3 failed combines in a row. Only a dud counts as a failure, not re-making a known pair. Any new discovery resets the count.
- Save to `localStorage` key `tinheart.v1` after every state change. Every storage access goes in try/catch. "Play again" clears the save.
- Reloading after the ending shows the finished, beating companion and Play again, without replaying the sequence.
- Installed parts stay on the Shelf, greyed out and marked installed. They can still be combined but can't be installed again.
- Layout: three panels on desktop. Below 760px they stack (Shelf, Crucible, Companion). Warm workshop palette. Art is inline SVG/CSS only.
- Sound is optional. If added, it's Web Audio only, starts after the first user gesture, and has a mute toggle.
- `node_modules/`, `test-results/` and `playwright-report/` are git-ignored.
- `conversation-history.txt` is maintained by the main session. Implementers do not edit it.
- Work happens directly on `main` (the repo exists only for this project).

## Review Focus

1. **Corrupted or foreign save data** (non-JSON, or JSON missing fields): the game starts fresh with no error. Owner: Task 2.
2. **Storage that throws** (private mode, blocked site data): the game is fully playable, it just doesn't persist. Owner: Task 4.
3. **Combine pressed with an empty slot, or double-clicked quickly**: no failure counted, no duplicate items, and the counter is unchanged after the second click. Owner: Task 3.
4. **Opened from `file://`**: loads, and combining works. Owner: Task 5.
5. **Every craftable recipe already found, but parts not yet installed**: the hint area tells the player to install parts instead of showing nothing or crashing. Owner: Task 2.

## DOM contract (used by every UI task and test)

| Selector | Element |
|----------|---------|
| `[data-item="<id>"]` inside `#shelf` | Shelf item button. Gets class `selected` when selected and `installed` when installed |
| `#slot-a`, `#slot-b` | Crucible slots. Attribute `data-filled="<id>"` or empty |
| `#combine` | Combine button, `disabled` unless both slots are filled |
| `#message` | Feedback line (flavor, "nothing happens", "already known") |
| `#crucible.smoke` | Class added for about 800 ms on a dud |
| `#found-count` | Text `"<n> / 20"` |
| `#recipe-book li` | One entry per found recipe, text `"<A> + <B> → <Result>"` |
| `#hint` | Hint text, hidden (`hidden` attribute) when there is no hint |
| `[data-slot="<slotId>"]` inside `#chest` | Chest slot. `data-installed="<id>"` once filled. Class `shake` on rejection |
| `#companion.alive` | Class once all 5 are installed |
| `#ending` | Ending panel, visible only when finished |
| `#play-again` | Button inside `#ending` |
| `#mute` | Mute toggle (only if sound is implemented) |

Item ids (snake_case): `brass, ember, quicksilver, moth_wing, molten_brass, living_vapor, silver_feather, gilded_wing, spark, gear, mirror_drop, cog_shell, ticking_gear, breath, flutter_membrane, glow_glass, lightning_bead, left_chamber, right_chamber, flutter_valve, spark_core, rhythm_spring, ash, firefly`.

Slot ids equal the heart-part ids: `left_chamber, right_chamber, flutter_valve, spark_core, rhythm_spring`.

### Task 2: Game state logic and persistence

**Files:**
- Modify: `index.html` (logic section of the script)
- Test: `tests/logic.spec.js`

**Interfaces:**
- Consumes: `ITEMS`, `RECIPES`, `STARTING_ITEMS`, `HEART_SLOTS`, `findRecipe` (Task 1).
- Produces, on `window.TinHeart` (all pure. They return new objects and never mutate their input):
  - `State = {discovered: id[], installed: Record<slotId, id>, failStreak: number, hint: string|null, finished: boolean}`
  - `newState(): State`. `discovered` = `STARTING_ITEMS`, everything else empty/zero/null/false.
  - `combine(s: State, a: id, b: id): {state: State, outcome: 'new'|'known'|'dud', result: id|null}`
  - `install(s: State, item: id, slot: slotId): {state: State, ok: boolean}`. `ok` only when `item === slot`, the item is discovered, the slot is empty and the game isn't finished. Sets `finished` when all 5 slots are filled.
  - `foundCount(s: State): number` = `discovered.length - 4`
  - `pickHint(s: State): string` (only called once `failStreak >= 3`)
  - `saveState(s: State): void`, `loadState(): State|null`, `clearSave(): void`. Key `tinheart.v1`. All wrapped in try/catch.
